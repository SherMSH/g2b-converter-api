## Основной стек

| Категория | Технология | Версия | Почему |
|-----------|-----------|--------|--------|
| Язык | Go | 1.25.0 | статическая типизация для разбора XML/JSON-контрактов, один бинарник в контейнере |
| HTTP-фреймворк | `gin-gonic/gin` | 1.12.0 | группы маршрутов и middleware из коробки; сервису нужен только роутинг |
| Логирование | `rs/zerolog` | 1.34.0 | структурированные JSON-логи с нулевыми аллокациями |
| Планировщик | `go-co-op/gocron` | 1.37.0 | периодические задачи (`ConvScanner`, переавторизация) без внешнего cron |
| Метрики | `prometheus/client_golang` | 1.23.2 | стандарт мониторинга в контуре |
| Кодировки | `golang.org/x/text` | 0.34.0 | windows-1251 ↔ UTF-8 при восстановлении кириллицы |
| XML / JSON | `encoding/xml`, `encoding/json` | stdlib | контракты покрываются тегами структур, сторонние парсеры не нужны |
| Криптография | `crypto/des`, `crypto/rsa`, `crypto/x509` | stdlib | 3DES/RSA для PIN-блоков |
| База данных | — | — | **не используется**, см. [Database.md](./Database.md) |
| Кеш | — | — | **не используется** |
| Очереди | — | — | **не используются** |

`go.mod` содержит также `mongo-driver`, `quic-go`, `sonic`, `goccy/go-json` — это транзитивные зависимости Gin и его кодеков, напрямую в коде они не вызываются.

## Инфраструктура

| Категория | Технология | Почему |
|-----------|-----------|--------|
| Контейнеризация | Docker, multi-stage build на Alpine | стандарт контура; итоговый образ — бинарник + config.json |
| Оркестрация | Docker Compose (один сервис на хосте) | одна инстанция, Kubernetes избыточен |
| Registry | GitLab Container Registry `gitlab.humo.tj:5050` | внутренний контур |
| CI/CD | GitLab CI, два stage: `build` → `deploy` | сборка на общем раннере, деплой на выделенном `g2b-runner` |
| Базовые образы | внутренний Nexus (`hub.docker.humo.lab`) | во внешний Docker Hub контур не ходит |
| Мониторинг | Prometheus (`/metrics`) | — |
| Логи | stdout → `/app/logs/app.log` через redirect в команде compose | без агрегатора, чтение файлом на хосте |

## Тестирование

| Уровень | Технология | Покрытие |
|---------|-----------|----------|
| Unit | `go test` | **отсутствует** |
| Integration | — | отсутствует |
| E2E | ручная проверка на стенде | smoke по основным операциям |

Фактическая проверка перед мержем:

```bash
go build ./...
go vet ./...
```

Это самая слабая часть проекта: маппинг кодов статусов и сумм не покрыт ничем, регрессии ловятся только на стенде. Первые кандидаты на юнит-тесты — `utils.GetRqType`, таблицы `internal/utils/compass.go`, конвертеры дат, `crypto.Format0`.

## Дополнительные библиотеки

- **`gin-contrib` / валидатор `go-playground/validator`** — приходит вместе с Gin; используется только в `ShouldBindJSON` для `SetPIN`.
- **`golang.org/x/text/encoding/charmap`** — восстановление испорченной кириллицы (`utils.FixCyrillic`) и работа с windows-1251 в данных партнёра.
- **`google/uuid`** — транзитивная зависимость; собственные идентификаторы генерируются из времени (`utils.GenerateTimestampID`, `GenerateCompositeID`).

## Что НЕ используем и почему

- **База данных.** Сервис принципиально stateless: источник истины — процессинг D8. Появится требование аудита или ретраев — понадобится хранилище, это отдельное архитектурное решение.
- **ORM.** Следствие предыдущего пункта.
- **Брокер сообщений.** Асинхронность ограничена планировщиком gocron; объёмы OFFLINE-пакетов этого достаточно.
- **Swagger/OpenAPI.** Аннотации `@title`, `@version`, `@host` есть в шапке `cmd/main.go`, но генерация не подключена: основной контракт задан XSD-схемами Compass, а не OpenAPI.
- **Переменные окружения для конфигурации.** Сейчас всё в `config.json`; см. [Deployment.md](./Deployment.md#конфигурация).

## Версионирование зависимостей

- Версии зафиксированы в `go.mod` / `go.sum` точными значениями.
- В Dockerfile выполняется `go mod tidy` во время сборки — это может изменить набор зависимостей относительно закоммиченного состояния; при воспроизведении проблем сборки проверять в первую очередь.
- `GOPRIVATE=gitlab.humo.tj` выставляется в builder-стадии для внутренних модулей.
- Обновление мажорных версий — отдельным MR с проверкой на стенде.
